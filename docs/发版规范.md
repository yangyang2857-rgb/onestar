## 0. 适用范围、依据分级与三条原则

本项目是原生 Android 应用（包名 `com.yangyang2857rgb.onestar`），当前分发方式为 GitHub Release + 侧载安装，构建链路为 `build.sh` + `aapt2` + `d8` + `zig cc` + `tools/zip16k.py`，不使用 Gradle。

### 0.1 依据分级与冲突裁决

发版规范里的每一条，来源强度并不相同。混在一起写，会让「标准要求」和「个人习惯」看起来一样硬，所以先分级：

| 级别 | 来源性质 | 举例 | 执行态度 |
|---|---|---|---|
| A 强制 | 平台/商店的准入与运行机制 | Play 的 `versionCode` 不可复用、目标 API 门槛、分阶段发布规则 | 必须满足，无偏离空间 |
| B 标准 | 国际标准、W3C 规范、SemVer 原文 | ISO/IEC/IEEE 12207:2026、WCAG 2.2 SC 2.5.5/2.5.8、SemVer 11 条规则 | 按原文语义执行；本项目场景不适用时需写明理由 |
| C 实践 | 官方工程指南与成熟社区规范 | Keep a Changelog、Conventional Commits、DORA、Chromium 发布周期、Android 无障碍建议 | 默认采纳；偏离需记录原因 |
| D 自定 | 本项目经验阈值与流程约定 | PATCH 每周合并、PATCH ≤ 10 条改动、崩溃率门禁 0.5% | 可随实际情况调整，但调整要改本文 |

冲突裁决顺序：**A 强制 > B 标准 > C 实践 > D 自定**。同级冲突取更严者。凡是 D 级条目，文中一律标注「项目自定」，不得冒充标准原文。

### 0.2 三条原则

| 原则 | 含义 | 落地动作 |
|---|---|---|
| 可重复 | 同样的提交能构建出一致的包 | 构建脚本入库、依赖版本固定、APK 记 SHA-256 |
| 可回滚 | 出问题能退回上一个可用状态 | 每版 APK 归档、存储格式变更必须可逆或提前告知 |
| 可签字 | 每次发布都敢在 CHANGELOG 上署名 | 发布前检查表逐项打勾，缺项不发 |

三条原则都满足才叫「一次发布」，否则只是「打了一个包」。

## 1. 版本号规则

### 1.1 SemVer 2.0.0 的原文要求

SemVer 原文有一条容易被忽略的前提：**使用这套规则前，必须先声明「公共 API」**，版本号才承载「兼容 / 不兼容」的信息。本项目据此把公共 API 定义为：**存储行格式 + 用户可见的交互契约 + 构建/发布方式**，不是 Java 方法签名。

| 条款 | 原文要求（转述） | 本项目对应 |
|---|---|---|
| 格式 | `X.Y.Z`，非负整数，不得前补零 | `0.12.1` |
| 主版本 | 存在不兼容的公共 API 变更时递增 | 存储格式不兼容、包名/签名/构建方式变更 |
| 次版本 | 以向下兼容方式新增功能时递增 | 新面板、新交互、新语言 |
| 修订 | 以向下兼容方式修缺陷时递增 | 手感、对比度、文案、适配 |
| 第 3 条 | **版本一经发行，禁止改变其内容**；任何修改都必须以新版本发行 | 已发 tag 不回填、不重打包 |
| 第 4 条 | `0.y.z` 属初始开发，任何东西都可能随时改变，公共 API 不应视为稳定 | 当前 `0.12.x` 允许调整交互契约 |
| 第 5 条 | `1.0.0` 用于界定公共 API 形成 | 对应版式与存储格式冻结 |
| 第 7 条 | 公共 API 的功能被标记弃用时，**必须**递增次版本号 | 弃用先出 MINOR，不能塞进 PATCH |
| 第 8 条 | 主版本递增时，次版本与修订号必须归零 | `0.12.1 → 1.0.0` |
| 第 9、10 条 | 先行版本用 `-` 后缀，构建元数据用 `+` 后缀；构建元数据不参与优先级比较 | `0.13.0-rc.1`、`0.13.0+build.7` |

### 1.2 与 Android 版本机制的关系

Android 官方文档明确：`versionCode` 是整数、`versionName` 是展示用字符串；系统用版本信息**防止降级安装**，因此 `versionCode` 必须单调递增且永不复用，上限为 2100000000。官方同时指出，多数开发者以语义化版本作为版本策略的基础——本项目正是如此，但两者不共用一套数字。

| 字段 | 取值 | 规则 |
|---|---|---|
| `versionName` | `0.12.1` | 按 1.3 递增，用于展示与 CHANGELOG |
| `versionCode` | `23`（当前 v6.7=22） | 独立整数流水，每次发版 +1，**不**由 versionName 派生 |

派生公式 `MAJOR×10000+MINOR×100+PATCH` 已废弃：历史流水号走到 6.7（派生值 60700），重编后 1.0.0 派生值仅 10000，会让系统判定为降级、拒绝覆盖安装。

### 1.3 本项目递增判定

| 位 | 触发条件 | 反例（不要这样升） |
|---|---|---|
| MAJOR | 存储格式不兼容（旧数据无法读取）、包名变更、构建方式更换、签名变更 | 只改 UI 布局 |
| MINOR | 用户可感知的新功能：新面板、新交互、新语言；或功能被标记弃用 | 只修对比度 |
| PATCH | 只修缺陷、调手感、改排版数值、改文案、适配系统设置、无障碍修复 | 塞进半个新功能 |

### 1.4 预发布与候选包

需要给他人试用又不想占正式号时，用 SemVer 先行版本号，例如 `0.13.0-rc.1`。先行版本的优先级低于同号正式版；同一主次修订号下，先行版本的先后按「点分标识符逐段比较、数字段按数值比较、纯数字段低于含字母段」判定，官方给出的示例链是：

```
1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta
          < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0
```

发布正式版后不再回改 rc 包内容。纯文档、注释、README 改动**不发版**，直接进 `main`。

### 1.5 为什么用 SemVer，而不用 CalVer

Calendar Versioning（CalVer，如 `2026.11.9`）是另一种成熟方案，官方文档写得很坦白：**CalVer 有意不表达破坏性变更**，因为「什么算破坏性变更」从来没有共识；它必须搭配 CHANGELOG 与基于时间的弃用政策才成立。同日多次发布时用 `YYYY.M.D.MICRO`。

| 维度 | SemVer 2.0.0 | CalVer |
|---|---|---|
| 传达兼容性 | 是，主版本即兼容性信号 | 否，官方明示不做此承诺 |
| 适合场景 | 有明确公共 API、下游需要判断兼容性 | 时间驱动发布（系统镜像、数据产品、月度版本） |
| 版本号信息量 | 兼容性 + 变更规模 | 发布日期 |
| 本项目适配 | 存储格式与交互契约需要兼容性信号 | 侧载用户不关心发布日期，关心「能不能直接覆盖装」 |

结论：本项目继续用 SemVer；若将来转为纯时间驱动分发（例如只做订阅式内容），再评估 CalVer，且必须同时补齐弃用政策与 CHANGELOG。

### 1.6 提交信息即版本决策（Conventional Commits 1.0.0）

Conventional Commits 规定提交信息结构 `<type>(<scope>): <description>`，并与 SemVer 一一对应，使「这次该升哪一位」不再靠感觉：

| 提交类型 | 含义 | 对应版本位 |
|---|---|---|
| `fix:` | 修缺陷 | PATCH |
| `feat:` | 新增功能 | MINOR |
| `feat!:` / `fix!:` / 正文含 `BREAKING CHANGE:` | 不兼容变更 | MAJOR |
| `docs:` `style:` `refactor:` `perf:` `test:` `build:` `ci:` `chore:` | 非功能性改动 | 不发版 |

执行细则：

- 一个提交只做一件事，禁止把「新功能 + 顺手改文案」混在一个 `feat` 里；
- 破坏性变更必须在 footer 写 `BREAKING CHANGE:` 并说明迁移方式，不能只靠 `!`；
- 发布时按本周期提交类型汇总，`feat` 决定是否够 MINOR，只有 `fix` 则为 PATCH；
- 提交类型是**决策依据**，不是自动发版开关——单人项目不引入自动发版，仍由检查表把关；
- 对「还在 0.x」不抱侥幸：Conventional Commits 的 FAQ 明确，初始开发阶段也应按已发布产品对待，因为总有人在使用；这与 SemVer 第 3 条（发行后内容不可改）一致。

### 1.7 明确禁止

- 禁止修改已发布版本的内容后仍用原版本号；
- 禁止复用或回退 `versionCode`；
- 禁止删除或重命名已发布 tag（GitHub 上会使对应 Release 退回草稿，已安装 APK 的版本号也无法回溯改写）；
- 禁止在构建元数据里藏语义（`+hotfix` 之类），构建元数据不参与优先级比较；
- 禁止编造版本号日期，无法确认时只写「未确认」。

## 2. 发版节奏

### 2.1 通道

| 通道 | 装什么 | 时限 | 附加约束 |
|---|---|---|---|
| 紧急修复 hotfix | 崩溃、数据丢失、安全问题、合规问题 | 确认后 24 小时内 | 单独发版，不夹带任何其他改动 |
| PATCH | 手感、对比度、文案、无障碍、系统适配 | 每周一次，当周小修**合并**成一次 | 不改存储格式 |
| MINOR | 一个能用一句话说清的新功能 | 2–4 周 | 必须带迁移验证与新增单测 |
| MAJOR | 破坏性变更 | 按需，一年一次也算勤 | 必须提供迁移说明与回退方案 |

### 2.2 列车模型：到点发车，不等功能

Chromium 的官方发布周期是本条的最佳参照：**Chrome 自 2026 年 9 月起改为每两周发一个新里程碑**（2021–2026 为四周一次；首班 Chrome 153 于 2026-09-08 进入 stable，桌面 / Android / iOS 同步），功能在分支点没做完就搭下一班车，不会为单个功能推迟发车；企业侧 Extended Stable 仍为每八周发一版，只回拣重要安全修复。

映射到本项目：

- **固定发车日**：每周日为 PATCH 车次，双周日为 MINOR 车次（项目自定，可按学期/工期调整）；
- **到点未完成的功能不上车**，回 `Unreleased`，等下一班；禁止「为等这一个功能，整列车晚点」；
- **hotfix 不打断列车**，它走独立通道，修完即发；
- 连续两个车次都空车，说明节奏定得过密，应合并车次而不是硬凑内容。

### 2.3 冻结与观察

- **发版前 24 小时冻结**：只允许修 bug，不允许加功能，否则永远在追移动的靶子；
- **发版后 48 小时观察**：不开新功能，否则新问题与旧问题混在一起无法归因；
- 冻结期内发现的非阻塞缺陷，一律记入 `Unreleased`，随下一班车走。

### 2.4 粒度

单次发布范围建议（项目自定）：PATCH ≤ 10 条改动、≤ 2 个模块；MINOR 一次只讲一个功能故事。超出说明攒得太久或切得太碎，两者都要改。

- 厂商 ROM 的字体度量差异（小米/华为等对 `fontScale` 的处理与 AOSP 不一致）

## 4. CHANGELOG 规范

依据 Keep a Changelog 1.1.0：日志写给人看、每个版本独立入口、同类改动分组、新版本在前、必须有发布日期、注明遵循语义化版本。官方也明说：**没有标准化的更新日志格式**，它提供的是「更好的范例」；以及用 `git log` 当 CHANGELOG 是糟糕做法。

**六类分组**：`Added` 新增 / `Changed` 变更 / `Deprecated` 弃用 / `Removed` 移除 / `Fixed` 修复 / `Security` 安全。空分类省略。

| 规则 | 做法 |
|---|---|
| `Unreleased` | 常驻顶部，发布时整块移入新版本小节 |
| 日期 | `YYYY-MM-DD`（ISO 8601），不写「昨天」「上周」 |
| 排序 | 版本倒序，版本内按「对用户的影响」排，不按提交顺序 |
| 撤包 | 已发布又撤下的版本保留条目并标 `[YANKED]`，不删除 |
| 写法 | 面向用户一句话说明「变了什么、对他有什么影响」，不搬 `git log` |
| 与版本号呼应 | 进 `Added` 通常意味着 MINOR，只进 `Fixed` 意味着 PATCH |
| 与 Release 关系 | GitHub Release 正文引用 CHANGELOG 对应小节，不另写一套说法 |

## 5. 灰度、观察与质量门禁

### 5.1 Google Play 的四个轨道

官方定义（若将来上架，按此执行）：

| 轨道 | 可见范围 | 用途 |
|---|---|---|
| 内部测试 Internal testing | 最多 100 名指定测试者 | 自测、熟人验包，秒级分发 |
| 封闭测试 Closed testing | 指定的一批测试者 | 小范围灰度、收集结构化反馈 |
| 开放测试 Open testing | 用户可从商店页自行加入 | 大样本预发布 |
| 正式版 Production | 所选国家/地区的全部用户 | 正式分发 |

### 5.2 分阶段放量

官方分阶段发布（staged rollout）要点：更新按**百分比**逐步放量；用户**随机**选取；暂停后再恢复，仍影响同一批用户；**首次发布不支持**分阶段；建议放量到 100% 后再改商店页文案与截图；放量期间可在 Release 面板监测崩溃与 ANR。

推荐分档（项目自定）：`5% → 20% → 50% → 100%`，每档至少观察 24 小时。触发暂停的条件见 5.3。暂停后修复以**新版本号**发布，`versionCode` 不可回退。

### 5.3 官方不良行为阈值与本项目门禁

Android vitals 的机制是明确的：Play 对**用户感知 ANR 率、用户感知崩溃率、耗电过高（表盘）、过度局部唤醒锁（Beta）**等核心指标设定了「不良行为阈值」，超出后应用在 Play 的曝光度可能降低，部分情况还会在商品详情页显示警告；另有「异常值」提示，用于发现指标的急剧变化。但**具体阈值数值并未作为固定常量公开**，而是在 Play Console 的 Android vitals 页面按应用显示，且 Google 保留调整权。

外部资料常引用的量级（供理解，非官方公开常量，不可当作标准原文）：整体用户感知崩溃率约 1.09%、ANR 约 0.47%；单手机型号崩溃率约 8%、ANR 约 5%。

关键结论：这是**商店的曝光度判定线**，不是发布门禁；拿它当门禁等于「已经被判不良行为才停」。本项目门禁更严（项目自定）：崩溃率 ≤ 0.5%、ANR ≤ 0.3%，**任一超标即暂停放量**；另有三条一票暂停项：出现数据丢失反馈、核心路径（记录写入/读取）不可用、覆盖安装失败。阈值若在 Play Console 看到与本节量级不同，以 Console 显示为准。

### 5.4 当前侧载分发的替代做法

没有商店灰度时，用「人工分档」替代：先自己 1 台真机 → 再 1–2 位熟人 → 再 GitHub Pre-release 公开 → 稳定后转正式 Release。每档之间至少隔一天。

**观察指标**（对应 5.3 与 DORA）：崩溃与 ANR、首启是否正常、数据是否完整、覆盖安装是否成功、用户反馈中的「回退/装回旧版」字样、发布后 48 小时内是否产生 hotfix。

## 6. 生命周期、弃用与停止支持

ISO/IEC/IEEE 12207 是软件生命周期过程的框架标准，现行版为 **12207:2026（第 2 版，2026-04 发布）**；2017 版已撤销（ISO 状态为 Withdrawn）。该标准覆盖从概念、开发、运行、支持到**退役（retirement/disposal）**的全生命周期，运行与维护是独立过程集。落到本项目：

| 阶段 | 做什么 | 出口条件 |
|---|---|---|
| 开发（0.y.z） | 快速迭代，允许破坏性改动 | 1.0.0：存储格式与版式冻结 |
| 维护（1.y.z） | 只做兼容性新增与修正 | 出现不兼容需求时进 2.0.0 |
| 停止支持（EOL） | 只修安全与数据损坏问题，其余回复「请升级」 | README 写 EOL 声明 |

**支持窗口**（项目自定）：只维护最近 2 个 MINOR 线；更老的版本仅处理安全与数据丢失问题。15 种语言 × N 个版本的全量回归成本极高，窗口必须收窄，否则验证会拖死发布。

**弃用流程**：先在一个 MINOR 里标 `Deprecated` 并在 CHANGELOG 写明替代方案 → 至少保留一个 MINOR 周期（SemVer 第 7 条要求弃用必须进 MINOR）→ 下一个 MAJOR 里 `Removed`。禁止静默删除用户可见功能。

**商店强制期限**：Google Play 每年上调目标 API 级别要求（例如 2025-08-31 起新应用与更新需目标 API 35），目标级别过低会限制应用在新系统设备上的可用性。具体年份门槛以当年官方公告为准，接到通知即排进 MINOR 计划，不拖到截止日。

**归档**：已发 tag 永久保留；APK + SHA-256 + CHANGELOG 条目三件套同时留档；权属证据包（署名版 APK、源代码归档）按版本或按里程碑归档。

## 7. 发布记录与 GitHub Release 操作

单人项目的现实：作者同时是产品、开发、测试、发布经理。因此「发布经理」职责靠清单固定，不靠记忆。

每个版本在 Release 页记录五行：`版本号`、`日期`、`提交 SHA`、`APK 字节数与 SHA-256`、`检查表结论`（通过 / 带风险项说明）。

仓库操作纪律（依据 GitHub 官方 Releases 文档）：

| 动作 | 规则 |
|---|---|
| 建 Release | **先存草稿**，附件齐全后再发布；仓库若启用 immutable releases，官方明确建议草稿先行，避免发布后无法补附件 |
| 预发布 | rc / beta 包发布时勾选「Pre-release」，不占用正式版语义，也不进「Latest」 |
| tag | 已发布 tag 不删除、不移动；删除 tag 会使对应 Release 退回草稿 |
| 正文 | 引用 CHANGELOG 对应小节，附安装说明与已知问题 |
| 撤包 | 保留 Release 并标注问题，另发修复版；不静默删除历史版本 |

## 8. 发布效能度量（DORA）

DORA 的交付效能指标用于观察趋势，官方定义：

| 指标 | 定义（转述） | 本项目怎么记 |
|---|---|---|
| 部署频率 Deployment frequency | 单位时间内成功发布到生产的次数 | 每月正式 Release 数 |
| 变更前置时间 Lead time for changes | 从提交进入主干到在生产成功运行的时间 | 提交日期 → Release 日期 |
| 变更失败率 Change fail rate | 部署后需要立即干预（回滚或 hotfix）的比例 | 需 hotfix 的发布数 ÷ 总发布数 |
| 失败部署恢复时间 Recovery time | 从失败部署到恢复所需时间 | 从发现到修复版发布的小时数 |

使用纪律：

- 四项一起看，不看单项。只看频率会鼓励「发得多」，只看失败率会鼓励「发得少」；
- 指标用于**自身趋势**，不用于跨项目对标；单人项目与团队项目没有可比性；
- 每次发布只记五行数字，季度回看一次，连续两个季度「变更失败率上升或恢复时间变长」就减速，先补测试与检查表，而不是加发版次数。

## 9. 标准适用性边界

写规范最怕「拿错尺子」，以下是本文引用标准的适用边界，避免误用：

| 依据 | 本来管什么 | 本项目怎么用 | 不能拿来做什么 |
|---|---|---|---|
| SemVer 2.0.0 | 有公共 API 的软件版本号 | 定义公共 API 后映射到存储/交互/构建 | 不能替代 CHANGELOG；不能保证兼容性，只做声明 |
| Keep a Changelog | 面向人的更新日志 | 六类分组、Unreleased、`[YANKED]` | 不是强制格式标准，官方自称「范例」 |
| Conventional Commits | 提交信息与语义化版本的联动 | 用提交类型决定升哪一位 | 不能替代人工发版决策 |
| Android versionCode | 平台升级/降级判定 | 独立整数流水 | 不能表达语义，不要塞语义 |
| Google Play 轨道与灰度 | 商店分发控制 | 上架后的放量方案 | 侧载场景没有等价机制，只能人工分档 |
| Android vitals 阈值 | 商店曝光度判定 | 作为「外部警戒线」参考 | 不是发布门禁，数值可能调整 |
| WCAG 2.2 | Web 内容无障碍 | 借用触控尺寸与对比度阈值 | 它不直接约束原生 Android，48dp 以 Android 官方建议为准 |
| Chromium Release Cycle | 浏览器发布列车 | 借用「到点发车」的节奏模型 | 周期长度不可照搬（四周是浏览器生态的选择） |
| ISO/IEC/IEEE 12207:2026 | 生命周期过程框架 | 借用阶段划分与退役概念 | 不规定版本号、灰度、CHANGELOG 的具体做法 |
| CalVer | 日历版本号 | 作为选型对照 | 不表达兼容性，本项目不采用 |

## 10. 一页速查

```
改文档 / 改注释      → 不发版，直接进 main
修 bug / 调手感      → PATCH，每周合并发一次
加功能 / 加语言      → MINOR，2–4 周，固定发车日
存储格式不兼容       → MAJOR，附迁移说明
崩溃 / 数据丢失      → hotfix，24 小时内，单独发

发版前 24h 只修 bug，发版后 48h 只观察
versionCode 每次 +1，已发 tag 永不删改
到点发车，功能没做完搭下一班
提交类型定版本位：fix→PATCH，feat→MINOR，BREAKING→MAJOR
触控 48dp、正文对比度 4.5:1
崩溃率 >0.5% 或 ANR >0.3% → 暂停放量
```
