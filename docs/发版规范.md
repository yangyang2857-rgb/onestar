# 拾光 OneStar · 发版规范

> 本文是项目唯一的发版依据。规则冲突时，以本文为准；本文与商店强制要求冲突时，以商店要求为准。
>
> 参考标准：语义化版本 2.0.0（SemVer）、Keep a Changelog 1.1.0、Android Developers《Version your app》、Google Play 分阶段发布与目标 API 级别要求、ISO/IEC/IEEE 12207:2017 软件生命周期过程。链接见文末。

## 0. 适用范围与三条原则

本项目是原生 Android 应用（包名 `com.yangyang2857rgb.onestar`），当前主要分发方式是 GitHub Release + 侧载安装，构建链路为 `build.sh` + `aapt2` + `d8` + `zig cc` + `tools/zip16k.py`，不使用 Gradle。

| 原则 | 含义 | 落地动作 |
|---|---|---|
| 可重复 | 同样的提交能构建出一致的包 | 构建脚本入库、依赖版本固定、APK 记 SHA-256 |
| 可回滚 | 出问题能退回上一个可用状态 | 每版 APK 归档、存储格式变更必须可逆或提前告知 |
| 可签字 | 每次发布都敢在 CHANGELOG 上署名 | 发布前检查表逐项打勾，缺项不发 |

三条原则都满足才叫「一次发布」，否则只是「打了一个包」。

## 1. 版本号规则

### 1.1 SemVer 2.0.0 的原文要求

| 条款 | 要求 | 本项目对应 |
|---|---|---|
| 格式 | 必须 `X.Y.Z`，非负整数，不得前补零 | `0.12.1` |
| 递增 | 主版本号：不兼容的公共 API 修改；次版本号：向下兼容的功能新增；修订号：向下兼容的问题修正 | 见 1.3 映射 |
| 第 3 条 | **版本发行后禁止改变该版本的内容**，任何修改都必须以新版本发行 | 已发 tag 不回填、不重打包 |
| 第 7 条 | 公共 API 的功能被标记为弃用时，**必须**递增次版本号 | 弃用先出 MINOR |
| 第 8 条 | 主版本号递增时，次版本号与修订号必须归零 | `0.12.1 → 1.0.0` |
| 第 4、5 条 | `0.y.z` 属初始开发阶段，API 不应视为稳定；`1.0.0` 界定公共 API 形成 | 当前 `0.12.x`，`1.0.0` 对应版式与存储格式冻结 |

对本项目而言，「公共 API」= **存储行格式 + 用户可见的交互契约 + 构建/发布方式**，不是 Java 方法签名。

### 1.2 与 Android 版本机制的关系

Android 官方文档明确两点：`versionCode` 是整数、`versionName` 是展示用字符串；系统用版本信息**防止降级安装**，因此 `versionCode` 必须单调递增、永不复用。官方也指出多数开发者以语义化版本作为版本策略基础——本项目正是如此，但两者不共用一套数字。

| 字段 | 取值 | 规则 |
|---|---|---|
| `versionName` | `0.12.1` | 按本文 1.3 递增，用于展示与 CHANGELOG |
| `versionCode` | `23`（当前 v6.7=22） | 独立整数流水，每次发版 +1，**不**由 versionName 派生 |

派生公式 `MAJOR×10000+MINOR×100+PATCH` 已废弃：历史流水号走到 6.7（派生值 60700），重编后 1.0.0 派生值仅 10000，会让系统判定为降级、拒绝覆盖安装。

### 1.3 本项目递增判定

| 位 | 触发条件 | 反例（不要这样升） |
|---|---|---|
| MAJOR | 存储格式不兼容（旧数据无法读取）、包名变更、构建方式更换、签名变更 | 只改 UI 布局 |
| MINOR | 用户可感知的新功能：新面板、新交互、新语言；或功能被标记弃用 | 只修对比度 |
| PATCH | 只修缺陷、调手感、改排版数值、改文案、适配系统设置、无障碍修复 | 塞进半个新功能 |

### 1.4 预发布与候选包

需要给他人试用又不想占正式号时，用 SemVer 先行版本号：`0.13.0-rc.1`。先行版优先级低于同号正式版，发布正式版后不再回改 rc 包内容。纯文档、注释、README 改动**不发版**，直接进 `main`。

### 1.5 明确禁止

- 禁止修改已发布版本的内容后仍用原版本号；
- 禁止复用或回退 `versionCode`；
- 禁止删除或重命名已发布的 tag（GitHub 上会使对应 Release 退回草稿，已安装 APK 的版本号也无法回溯改写）；
- 禁止编造版本号日期，无法确认时只写「未确认」。

## 2. 发版节奏

| 通道 | 装什么 | 时限 | 附加约束 |
|---|---|---|---|
| 紧急修复 hotfix | 崩溃、数据丢失、安全问题、合规问题 | 确认后 24 小时内 | 单独发版，不夹带任何其他改动 |
| PATCH | 手感、对比度、文案、无障碍、系统适配 | 每周一次，当周小修**合并**成一次 | 不改存储格式 |
| MINOR | 一个能用一句话说清的新功能 | 2–4 周 | 必须带迁移验证与新增单测 |
| MAJOR | 破坏性变更 | 按需，一年一次也算勤 | 必须提供迁移说明与回退方案 |

两条配套纪律：

- **发版前 24 小时冻结**：只允许修 bug，不允许加功能，否则永远在追移动的靶子；
- **发版后 48 小时观察**：不开新功能，否则新问题与旧问题混在一起无法归因。

单次发布范围建议：PATCH ≤ 10 条改动、≤ 2 个模块；超出说明攒得太久或切得太碎，两者都要改。

## 3. 发布前检查表（DoD）

全部打勾才允许出包。任何一项为否，降级为「内部测试包」，用 `-rc.N` 标记。

**构建**

- [ ] `build.sh` 全流程通过，无新增编译警告
- [ ] `versionCode` 已 +1，`versionName` 与 CHANGELOG 一致
- [ ] `tools/zip16k.py` 校验通过，`.so` 数据偏移 16384 对齐
- [ ] 签名与上一版一致（签名变更等于换应用，必须升 MAJOR 并告知）

**测试**

- [ ] 7 个测试类 221 项断言全绿
- [ ] 新增逻辑带对应单测（纯逻辑类优先，UI 逻辑抽成可测函数）
- [ ] 旧存储格式可读：`date` / `date:mood` / `date:mood:note` / 第 5 段补记标记
- [ ] 覆盖安装测试：旧版直接升新版不丢数据

**兼容与可用性**

- [ ] 15 种语言抽检（简中、繁中、英、阿、维、藏、日、韩至少各一条路径）
- [ ] 系统字号 0.90 / 1.0 / 1.15 三档无截断、无重叠
- [ ] 横竖屏切换、刘海/挖孔/矮屏不溢出
- [ ] 触控目标 ≥ 48dp；文字对比度 ≥ 4.5:1（大字号 ≥ 3:1，WCAG AA）
- [ ] TalkBack 能读出主界面状态与按钮语义

**文档与归档**

- [ ] CHANGELOG 的 `Unreleased` 已移入新版本小节，日期用 ISO 8601
- [ ] APK 归档并记录字节数与 SHA-256
- [ ] 上一版 APK 仍可获取（回退用）

## 4. CHANGELOG 规范

依据 Keep a Changelog 1.1.0：日志写给人看、每个版本独立入口、同类改动分组、新版本在前、必须有发布日期、注明遵循语义化版本。

**六类分组**：`Added` 新增 / `Changed` 变更 / `Deprecated` 弃用 / `Removed` 移除 / `Fixed` 修复 / `Security` 安全。空分类省略。

| 规则 | 做法 |
|---|---|
| `Unreleased` | 常驻顶部，发布时整块移入新版本小节 |
| 日期 | `YYYY-MM-DD`，不写「昨天」「上周」 |
| 排序 | 版本倒序，版本内按「对用户的影响」排，不按提交顺序 |
| 撤包 | 已发布又撤下的版本保留条目并标 `[YANKED]`，不删除 |
| 写法 | 面向用户一句话说明「变了什么、对他有什么影响」，不搬 `git log` |
| 与版本号呼应 | 进 `Added` 通常意味着 MINOR，只进 `Fixed` 意味着 PATCH |

## 5. 灰度与观察

### 5.1 若上架 Google Play

官方分阶段发布（staged rollout）要点：更新按百分比逐步放量；用户**随机**选取，暂停后再恢复仍影响同一批用户；只能用更新，**首次发布不支持**；建议放量到 100% 后再改商店页文案与截图。

推荐分档：`5% → 20% → 50% → 100%`，每档至少观察 24 小时。触发暂停的条件（项目自定经验阈值，非官方标准）：崩溃率 > 1%、出现数据丢失反馈、核心路径不可用。暂停后修复以**新版本号**发布，`versionCode` 不可回退。

### 5.2 当前侧载分发的替代做法

没有商店灰度时，用「人工分档」替代：先自己 1 台真机 → 再 1–2 位熟人 → 再 GitHub Pre-release 公开 → 稳定后转正式 Release。每档之间至少隔一天。

**观察指标**：崩溃与 ANR、首启是否正常、数据是否完整、用户反馈中的「回退/装回旧版」字样。

## 6. 生命周期、弃用与停止支持

ISO/IEC/IEEE 12207:2017 把软件生命周期划分为从概念到**退役（retirement）**的过程集，运行与维护是独立过程。落到本项目：

| 阶段 | 做什么 | 出口条件 |
|---|---|---|
| 开发（0.y.z） | 快速迭代，允许破坏性改动 | 1.0.0：存储格式与版式冻结 |
| 维护（1.y.z） | 只做兼容性新增与修正 | 出现不兼容需求时进 2.0.0 |
| 停止支持（EOL） | 只修安全与数据损坏问题，其余回复「请升级」 | README 写 EOL 声明 |

**支持窗口**：只维护最近 2 个 MINOR 线；更老的版本仅处理安全与数据丢失问题。15 种语言 × N 个版本的全量回归成本极高，窗口必须收窄，否则验证会拖死发布。

**弃用流程**：先在一个 MINOR 里标 `Deprecated` 并在 CHANGELOG 写明替代方案 → 至少保留一个 MINOR 周期 → 下一个 MAJOR 里 `Removed`。禁止静默删除用户可见功能。

**商店强制期限**：Google Play 每年上调目标 API 级别要求（2025-08-31 起新应用与更新需目标 API 35），目标级别过低会限制应用在新系统设备上的可用性。具体年份的门槛以当年官方公告为准，接到通知即排进 MINOR 计划，不拖到截止日。

**归档**：已发 tag 永久保留；APK + SHA-256 + CHANGELOG 条目三件套同时留档；权属证据包（署名版 APK、源代码归档）按版本或按里程碑归档。

## 7. 角色与发布记录

单人项目的现实：作者同时是产品、开发、测试、发布经理。因此「发布经理」职责靠清单固定，不靠记忆。

每次发布在 Release 页记录五行：`版本号`、`日期`、`提交 SHA`、`APK 字节数与 SHA-256`、`检查表结论`（通过 / 带风险项说明）。

## 8. 一页速查

```
改文档            → 不发版，直接进 main
修 bug / 调手感    → PATCH，每周合并发一次
加功能 / 加语言    → MINOR，2–4 周
存储格式不兼容     → MAJOR，附迁移说明
崩溃 / 数据丢失    → hotfix，24 小时内，单独发
发版前 24h 只修 bug，发版后 48h 只观察
versionCode 每次 +1，已发 tag 永不删改
```
