# 凭据与令牌管理

本文件规定拾光 OneStar 仓库在**自动化提交、CI 发布、签名注入**三条链路上如何使用访问令牌与密钥。目标是让"令牌只在内存里活一次"，任何一次提交都不应该在磁盘、提交历史、日志或聊天记录里留下可复用的凭据。

> ⚠️ 本文件**只记录规则与流程，不记录任何真实凭据值**。看到本文档里出现形如 `github_pat_…`、`ghp_…` 的完整字符串，一律视为泄露事故，按 §5 处置。

## 1. 令牌类型：只用 fine-grained，不用 classic

| 类型 | 是否允许 | 说明 |
| --- | --- | --- |
| Fine-grained personal access token（`github_pat_`） | ✅ 唯一允许 | 可限定单一仓库 + 逐项权限 + 强制过期 |
| Classic PAT（`ghp_`） | ❌ 禁止新签发 | 权限粒度只有 scope，一旦泄露等于全账号仓库可写 |
| GitHub App installation token | ✅ 推荐（长期方案） | CI 内由 App 私钥换取，1 小时自动过期，无需人工轮换 |
| 账号密码 / OAuth 用户 token 提权 | ❌ 禁止 | — |

历史遗留的 classic token 必须吊销，不得以"还没到期"为理由继续使用。

## 2. 权限最小化：改 `.github/workflows` 必须额外开 Workflows

Fine-grained token 的权限是逐项勾选的，**默认不含工作流权限**。这会导致一个很容易误判的现象：

- 提交普通文件（`README.md`、`docs/**`、`build.sh`）→ 成功；
- 同一个 commit 里带上 `.github/workflows/*.yml` → `403 Resource not accessible by personal access token`。

原因不是 token 失效，而是缺少 `Workflows` 权限。用 Git Data API 造 tree 时，只要 tree 里出现 workflow 路径，整个 tree 创建请求就会被拒——**不是只有那个文件失败，是整批失败**。

### 2.1 推荐勾选清单

| 权限项 | 级别 | 用途 |
| --- | --- | --- |
| `Contents` | Read and write | 读写文件、建 commit、推分支 |
| `Workflows` | Read and write | 修改 `.github/workflows/**`（**改 CI 必开**） |
| `Metadata` | Read（自动附带，不可取消） | 仓库基础信息 |
| `Actions` | Read | 可选，用于查 CI 运行状态 |
| 其他（`Secrets` / `Administration` / `Packages` …） | ❌ 不开 | 除非有明确的当前需求 |

### 2.2 仓库范围与有效期

- **Repository access 必须选 "Only select repositories"**，且只勾 `onestar`，不要用 "All repositories"。
- **Expiration 不超过 30 天**；一次性运维任务建议 7 天。
- 令牌备注（Note）写清用途与到期日，例如 `onestar-docs-push-2026-11`，便于在设置页面上识别哪个该删。

### 2.3 权限不足的实测判别法

不要靠猜。用两次对照请求确认：

1. 用同一 token 建一个只含普通文件的 tree → 成功，说明 `Contents` 没问题；
2. 再建一个只多加 `.github/workflows/<某个文件>` 的 tree → 403，说明缺 `Workflows`。

确认后**不要重试第三次**，直接去令牌设置页补权限（补完权限后 token 值不变，不需要重新签发），或先把不含 workflow 的文件拆成单独 commit 提交，workflow 文件等补齐后再补一次提交。

## 3. 传递方式：环境变量，禁止写进代码

这是本仓库踩过的真实事故形态：**把 token 拼进 Python 脚本字符串里再执行**。脚本会被框架自动落盘到工作区，结果是"令牌明文写进了磁盘文件"，而提交时这一层根本没被考虑到。

### 3.1 硬性规则

| 场景 | 正确做法 | 禁止做法 |
| --- | --- | --- |
| 脚本读取令牌 | `os.environ["GITHUB_TOKEN"]` | 代码里写字面量、`.py` 常量、注释 |
| 命令行传参 | `curl -H "Authorization: Bearer $GITHUB_TOKEN"` | 把值直接写进命令字符串（会进 shell 历史与工具日志） |
| 本地配置 | 不进任何仓库内文件 | 提交 `.env`、`token.txt`、`*.pem` |
| CI 发布 | GitHub Actions Secrets（签名口令、keystore） | 明文写在 workflow 的 `env:` 里 |
| 聊天/文档中传递 | 由令牌所有者本人在会话临时发送，用完即吊销 | 写进 issue、PR 描述、文档、截图 |

### 3.2 `.gitignore` 基线

仓库根 `.gitignore` 至少包含：

```
*.pem
*.jks
*.keystore
.env
.env.*
token.txt
```

注意：`.gitignore` 只防"误提交"，**不防已经写入磁盘的泄露**。令牌一旦被任何工具落盘，正确处置是吊销，而不是删除文件了事。

## 4. 提交前自检（每次用令牌前跑一遍）

1. `git status` / 工作区扫描：确认没有未跟踪的 `.env`、`token.txt`、脚本副本。
2. 全目录搜索令牌前缀：`grep -rn "ghp_\|github_pat_" .`，期望命中 0（文档中讨论格式时用 `github_pat_…` 省略写法）。
3. 确认本次提交的路径清单里**是否含 `.github/workflows/**`**，含则核对 §2.1 权限。
4. 提交信息（commit message）里不写任何凭据、内网地址、服务器口令。
5. 提交完成后，令牌**立即吊销**（一次性运维任务），或在任务清单里写明到期日。

## 5. 泄露处置流程

发现令牌出现在提交历史、日志、磁盘文件、聊天记录、公开页面时，按顺序执行：

1. **立刻吊销**：GitHub → Settings → Developer settings → Personal access tokens → 对应令牌 Delete。先吊销，再排查，不要边排查边留着。
2. **确认影响面**：查该令牌权限范围内的仓库、以及 GitHub 账号的 Security log / 审计日志，看是否有异常 commit、分支创建、workflow 触发。
3. **清理落盘副本**：删除含明文的脚本/日志文件，并检查是否已被打包进压缩包、diff、报告类产物。
4. **改写历史（仅在已推送且确属敏感时）**：用 `git filter-repo` 或 BFG 清除历史中的令牌字符串，随后强制推送并通知协作者重新 clone。**已公开过的令牌即使改写历史也不算安全，吊销仍是唯一有效动作。**
5. **重新签发**：按 §2 重新生成，权限只勾当前需要项，有效期从短。
6. **记录**：在本文档 §7 追加一条事故记录（写现象与原因，不写令牌值）。

## 6. CI 与签名凭据

- 签名 keystore 与口令只存在于 GitHub Actions Secrets（`KEYSTORE_BASE64`、`KEYSTORE_PASSWORD`、`KEY_ALIAS`、`KEY_PASSWORD`），构建时临时还原、用完即弃，不落仓库、不进构建产物。
- workflow 中的 `${{ secrets.* }}` **不会**被打印；一旦用 `echo` 或 `set -x` 输出，会被 GitHub 自动打码，但仍应在日志审查中确认没有 `***` 之外的可疑明文。
- 验签流程与证书固定细节见 [签名与覆盖升级.md](签名与覆盖升级.md)。
