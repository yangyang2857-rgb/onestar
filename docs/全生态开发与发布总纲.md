## 0. 这份文档怎么用

六份平台要点各自成篇，回答的是"这个平台怎么做不出岔子"；本文回答的是**六个平台放在一起时，哪些是同一件事、哪些是必须分头做的事、什么时间点必须做完**。

三种用法，不必通读：

| 你的处境 | 直接看 | 目的 |
| --- | --- | --- |
| 排期 / 定里程碑 | §2 全局时间表、§7 风险矩阵 | 找出卡死发版的那几个日期 |
| 现在要动手写代码 | §3 身份与签名锚点、§5 跨平台共性矩阵 | 先定死不可逆的锚点，再决定抽象层 |
| 马上要发版 | §6 统一发布闸门、§4 对应平台节 | 逐项过闸，不跳项 |

**标记约定**

- ⛔ = 踩了就直接失败（提交不进去 / 装不上 / 审核被拒 / 用户数据风险），无商量空间
- 🟡 = 质量红线，不违规但会显著降低转化或体验
- ✅ = 已联网核实，与官方当前口径一致
- 🔄 = 与源文档不一致，本文已修正（详见 §8）
- 文中所有日期均以 2026-11-10 为基准判断"已生效 / 待生效"

**与源文档的关系**：本文是总纲与索引，不是源文档的替代品。具体命令、代码片段、逐项清单原文保留在 `docs/ecosystems/` 下六份文件里，本文只做三件事——抽取红线、对齐冲突、建立跨平台统一口径。

## 1. 全局红线分层：三个失效面

六个平台的失败方式不同，但坍缩点只有三类。按这三类组织，比按平台组织更容易发现"以为通用、其实各处不一致"的地方。

### 1.1 第一层：发不出去（构建/上传/提交阶段就被拦）

| 平台 | 首要拦截点 | 触发后果 |
| --- | --- | --- |
| Android | targetSdk 低于 36；含原生库未 16 KB 对齐 | Play Console 拒绝接收上传包 |
| Apple | SDK 低于 iOS 26 / watchOS 26 / visionOS 26 / tvOS 26 | App Store Connect 拒收构建 |
| Windows | MSIX 清单/签名不合规；EXE/MSI 非离线自托管 | Partner Center 提交失败 |
| HarmonyOS | `deviceTypes` 使用 `default`；证书过期；元服务单包超 2 MB | 无法上架 / DevEco 打包失败 |
| Linux | glibc 基线过高；.rpm 未 GPG 签名 | 包能传上去但用户装不上，dnf 直接拒装 |
| Web | CSP 配置错误导致资源全被拦；构建产物不可复现 | "部署成功"但页面白屏 |

### 1.2 第二层：装不上（用户在设备上装不成功 / 打不开）

| 平台 | 典型场景 | 根因 |
| --- | --- | --- |
| Android | 折叠屏展开后布局崩、手表包过大装不下 | 按设备名写死布局；手表未单独瘦身 |
| Apple | macOS 官网下载的 dmg 提示"已损坏" | 未公证或未 staple |
| Windows | 首次下载被 SmartScreen 拦"无法识别的应用" | 未签名或信誉未积累（EV 也无用） |
| HarmonyOS | GT 系列手表装 ArkTS HAP 报"解压失败" | 误把 liteWearable 当 wearable |
| Linux | Ubuntu 22.04 上启动即崩 | 在 Ubuntu 24.04 上构建，glibc 符号版本不满足 |
| Web | 添加到主屏后无法安装 | manifest 缺 192/512 图标或 start_url |

### 1.3 第三层：审核被拒（人工/自动审核环节）

六个平台的拒审原因高度收敛，几乎全部落在**"声明与实际行为不一致"**：

```
权限声明 → SDK 实际行为 → 网络请求 → 商店隐私表单 → 隐私政策文档
```

这条链上任何一环对不上，结论都是拒审。Android 叫 Data Safety，Apple 叫 App Privacy + Privacy Manifest，Windows 叫隐私申报 + 同意顺序，HarmonyOS 叫 AGC 隐私标签，Linux/Web 无审核但对应的是真实的合规与法律责任。**这不是五套规则，是一套规则的五种表述**，统一处理见 §5.3。

另有三条跨平台共性拒审项：隐私政策 URL 无效（指向主页/PDF/需登录）、权限描述空泛（只写"需要相机"）、同意顺序错误（弹窗未关先发请求）。

## 2. 全局时间表

以 2026-11-10 为基准。**已生效项代表"现在不满足就发不出去"，不是"将来要注意"。**

### 2.1 已生效（必须已经在做）

| 日期 | 平台 | 要求 | 状态 |
| --- | --- | --- | --- |
| 2025-10-14 | Windows | Windows 10 终止支持；**消费者 ESU 至 2026-10-13 结束，商业/企业 ESU 最长可续至 2028-01** | ✅ 已生效，Windows 10 不再有常规安全更新 |
| 2025-11-01 | Android | target API 35+ 且含原生库的应用，64 位 .so 必须 16 KB 对齐 | ✅ 已生效；**2027-02-01 起不合规的更新将被 Play 直接拒收**（见 §2.2） |
| 2026-04-28 | Apple | 上传必须使用 iOS/iPadOS 26、watchOS 26、visionOS 26、tvOS 26 SDK 或更高 | ✅ 已生效 |
| 2026-08 | Android | Android TV 应用必须支持 64 位（16 KB 对齐按 2025-11-01 的 target API 35+ 通用条款执行，TV 无单独强制日） | ✅ 已生效（官方口径为"8 月起"，具体日以 Play 政策页为准） |
| 2026-08-31 | Android | 新应用与更新必须 target API 36；Wear OS / AAOS 最低 API 35；**TV / XR 最低 API 34** 🔄 | ✅ 已生效（延期通道已于 2026-11-01 关闭） |
| 2026-09 | Apple | macOS 27 发布，仅支持 Apple Silicon；macOS 26 为最后一个支持 Intel 与 Rosetta 的版本 | ✅ 已发生（Apple 2026-09-09 仅称"即将面向用户发布"，未公布具体上架日），arm64 only 是当下要求而非规划 |
| 2026-09-15 | Android | 含原生代码的 Wear OS 应用，**除提供 32 位版本外还必须提供 64 位版本**（仅 64 位不违规，32 位支持政策不变） | ✅ 已生效 |

### 2.2 未来 12 个月（排期必须排进去）

| 日期 | 平台 | 要求 | 现在该做什么 |
| --- | --- | --- | --- |
| 2027-02-01 | Android | Play 拒绝接收不支持 16 KB 页面大小的应用更新（不只是新应用） | 现在就扫全部 `.so` 与传递依赖 SDK；`tools/zip16k.py --check` 进 CI |
| 2027-04（**推断**） | Apple | 上传门槛抬升至 iOS 27 / iPadOS 27 / tvOS 27 / visionOS 27 / watchOS 27 SDK（按 Apple 历年节奏推断，**官方尚未公告**） | Xcode 27 已正式发布，2027 年 1 月前完成工程迁移 |
| API 37 生效后 | Android | 大屏（sw > 600dp）方向锁定与禁止 resize 的 opt-out 被移除 | 现在就移除 `screenOrientation` 锁定与 `resizeableActivity=false` 依赖 |
| 滚动 | HarmonyOS | 发布证书 3 年有效期，到期前 3 个月邮件提醒 | 建立到期监控；续期用原 .p12 + .csr，不重新生成密钥 |
| 滚动 | Apple | TestFlight 构建 90 天过期 | 发版节奏与 90 天窗口对齐 |

### 2.3 无硬日期但已在生效的"隐性时间表"

- **Windows SmartScreen 信誉**：每个新版本从零开始积累，需数周 + 数百次全新安装。这意味着"提前一个月发预览版"实际上是信誉预热期，应写进发布计划。
- **Linux glibc 基线**：一旦提高基线（例如迁到 Ubuntu 24.04 构建），旧用户会永久失去更新能力，属于不可逆动作，只能通过长期维护双构建线回退。
- **HarmonyOS App ID / Linux .desktop 与 app_id**：改动会断裂任务栏固定、通知历史、窗口分组，且用户侧无法自动修复。

## 3. 身份与签名锚点（写代码前一次定死）

跨平台最贵的错误不是 bug，是**同一款应用在不同平台被用户认成两个应用**。以下锚点在第一个 beta 前锁定，之后只增不改。

### 3.1 身份锚点

| 锚点 | 取值 | 平台 | 改动代价 |
| --- | --- | --- | --- |
| 应用包名 / applicationId | `com.yangyang2857rgb.onestar` | Android | 不可改，等于换新应用 |
| Bundle ID | `com.yangyang2857rgb.onestar` | Apple 全平台 | 不可改，IAP 与订阅全部失效 |
| HarmonyOS bundleName | `com.yangyang2857rgb.onestar` | HarmonyOS | 不可改，用户需卸载重装 |
| MSIX 包标识 / Publisher | `CN=Nightglean Studio` | Windows | 改为不同 Publisher 等于新产品 |
| Linux App ID / .desktop 名 / 窗口 app_id | 三者必须完全一致，Flatpak 下还与 Flatpak ID 一致 | Linux | 断裂任务栏固定与通知历史 |
| Web 源站（origin） | 正式域名，一次定死 | Web | origin 变化导致 PWA 重装、Storage 分区数据丢失、OAuth 回调失效 |

> 工作室主体已定稿：**长夜拾星 / Nightglean Studio**。证书 Subject、商店卖家名、MSIX Publisher 统一使用该主体名，不使用个人姓名。

### 3.2 签名材料与托管

| 平台 | 签名材料 | 有效期 | 托管位置 |
| --- | --- | --- | --- |
| Android | 上传密钥（.jks）+ Play App Signing 应用签名密钥由 Google 持有 | 建议 25 年+ | GitHub Secrets；应用签名密钥不可导出，丢失需走 Play 重置流程 |
| Apple | App Store 分发证书 + Provisioning Profile；macOS 用 Developer ID Application | 1 年（证书） | CI Secrets；每 12 个月轮换 |
| Windows | OV/EV 证书或 Azure Artifact Signing | 1–3 年 | Azure Key Vault / GitHub Secrets |
| HarmonyOS | 发布证书 .cer + 发布 Profile .p7b + 密钥库 .p12 | **3 年**（调试证书 180 天 / 未实名 14 天） | GitHub Secrets（base64） |
| Linux | AppImage GPG 密钥、.rpm GPG 密钥、MOK 密钥（如含内核模块） | 长期 | Secrets；公钥随发布页公布指纹 |
| Web | 发布签名 / SRI 哈希、部署 OIDC 凭据 | 短期 | OIDC 临时凭据，不使用长期密钥 |

### 3.3 三条跨平台通用的密钥纪律

1. **签名材料永不进 Git**：`.keystore`、`.jks`、`.p12`、`.cer`、`.p7b`、`.pfx`、GPG 私钥、MOK 私钥，一律 Secrets。
2. **CI 内临时落地、用完即删、不打印日志**；Secret 只注入真正消费它的 step，不注入整个 job。
3. **生产签名加 environment gate**，任何 PR 合并都不能直接触达发布密钥。

## 4. 分平台总纲

每节只保留"决定成败"的内容；完整清单见 `docs/ecosystems/` 对应文件。

### 4.1 Android

**交付形态**：Play 生产发布一律 `.aab`（启用 Play App Signing）；`.apk` 仅用于 GitHub Releases / F-Droid / 企业内部分发；`.apks` 只做本地测试。

**硬约束**
- ⛔ targetSdk：手机 36、Wear OS / AAOS 35、**TV / XR 34**（🔄 源文档将 TV 与手机混为一档，官方口径是 34）。
- ⛔ 含原生库的应用，64 位 .so 必须 16 KB 对齐，且要穿透检查每一个传递依赖的第三方 SDK——一个 4 KB 对齐的 SDK 就会让整个包被判不通过。
- ⛔ 大屏（sw > 600dp）不得锁方向、不得 `resizeableActivity=false`；API 37 起无 opt-out。
- 🟡 Wear OS 独立瘦身：典型设备 RAM 1–2 GB，>5 MB 显著影响下载意愿；表盘环境模式 ≤10 MB、交互模式 ≤100 MB。

**适配主线**：一套 Compose + `WindowSizeClass`（compact / medium / expanded）驱动手机、折叠屏、平板，不为三种形态维护三套逻辑。折叠屏分界对齐折叠边/铰链，状态用 ViewModel / `rememberSaveable` 跨配置变更保留。

**合规链条**：Manifest 权限 → 第三方 SDK 实际行为 → 网络请求 → Data Safety 表单 → 隐私政策，五环对齐。高频拒审 TOP3：Data Safety 与实际不符、权限最小化不过关、隐私政策 URL 无效。

### 4.2 Web

**交付形态**：无统一审核闸门，也就没有兜底——一次错误发布直接触达全部线上用户。发布 = 不可变构建 + 原子回滚。

**硬约束**
- ⛔ 全站 HTTPS，不允许"后台 HTTPS、静态资源 HTTP"的混合内容；`localhost` 除外。
- ⛔ 可安装性门槛在 manifest：`name`/`short_name`、192px + 512px 图标、`start_url`、`display`；Service Worker 已不是安装硬门槛，但离线与推送仍依赖它。
- ⛔ CSP 用 nonce/hash-based strict CSP + Trusted Types，不做域名 allowlist（历史研究显示 94.72% 的 allowlist 策略可被绕过）。
- ⛔ 性能是及格线不是优化项：LCP ≤ 2.5 s、**INP ≤ 200 ms**、CLS ≤ 0.1，CI 设预算，低于阈值阻断合并。
- ⛔ **托管能力必须前置选型**：GitHub Pages 不支持自定义响应头（CSP / HSTS 无法下发）、无 rewrite、`*.github.io` 不可备案；Cloudflare Pages 用 `_headers` / `_redirects` 可满足，但有文件数与单文件体积上限（20000 文件 / 25 MiB 量级）且免费层无 SLA。先确认响应头能否下发，再谈框架与性能预算（详见 `ecosystems/Web…要点.md` §6.4）。

**适配主线**：组件布局用容器查询（`@container`，2025-08 起 Baseline Widely available），视口媒体查询只用于页面级切换；暗黑模式走 `prefers-color-scheme` + CSS 变量，禁止颜色反转与硬编码色值；触摸目标 ≥ 44×44 px。

**回滚语义**：代码 + CDN 缓存 + Service Worker + 数据库迁移四层一起回滚；不可逆迁移必须有前滚方案；回滚后必须验证错误率、API 成功率、CWV，而不是"部署成功"即结束。

### 4.3 HarmonyOS

**交付形态**：用户侧安装单元是**已签名的 `.hap`**（GitHub Release 直接放 HAP）；`.app` 是分发容器，不作主安装包；`.har`/`.hsp` 是开发期共享包。

**硬约束**
- ⛔ `deviceTypes` 必须覆盖全部目标设备且不用 `default`（可编译、不可上架）；平板要声明 `tablet`、PC 声明 `2in1`，否则会被"兼容分发"稀释为无原生大屏体验。
- ⛔ 发布证书 3 年、调试证书 180 天；过期不能延期，只能用原 `.p12` + `.csr` 重签新的 `.cer`/`.p7b`。
- ⛔ 元服务：Stage 模型下**任意单个包 ≤ 2 MB**、**同一设备类型下所有包总和 ≤ 10 MB**（华为《元服务规格》原句，2026-09-29 更新）。注意与本项目直接冲突的一条：**元服务包内不得含 SO 文件**——本项目含 JNI 原生库，这条等于元服务形态必须放弃全部原生加速，只适合做纯 ArkTS 的轻量入口，不能承载主 App。
- ⛔ 轻量手表（`liteWearable`）不支持 ArkTS HAP、不支持 C/C++、不支持 Promise/async：GT/Fit 系列必须走 JS/TS + `.hmp`/`.bin`，工程内只允许 JS 文件。

**适配主线**：600vp 断点驱动（<600vp 单栏，≥600vp 双栏/多栏），不按 deviceType 写死；折叠屏悬停态用 `FolderStack` / `FoldSplitContainer`，折痕用 `getCurrentFoldCreaseRegion()`，返回空时以 16vp 合成中线兜底；宽屏（Pura X View 类）单独回归圆角安全区。

**合规**：TOP1 是"用户同意隐私政策前获取信息或权限"；TOP2 是"申请了权限但无有效使用场景"（`reason` 必须写清用途，不能只写"需要定位"）。

### 4.4 Apple

**交付形态**：App Store 走 `.ipa` + App Store 分发证书 + Provisioning Profile；TestFlight 是发版前最后一道真实设备关（内部 100 人免审，外部 10,000 人首个构建需 Beta App Review，构建 90 天过期）；macOS 官网直装必须 Developer ID 签名 → Hardened Runtime → `notarytool` 公证 → `staple`，四步顺序不可错。

**硬约束**
- ⛔ SDK：2026-04-28 起 iOS/iPadOS 26、watchOS 26、visionOS 26、tvOS 26（官方已公告）；2027-04 起全面抬至 27（按历年节奏推断，**官方尚未公告**）。
- ⛔ macOS 27 起仅 Apple Silicon，构建架构 `arm64 only`；macOS 26 是最后一个支持 Intel 与 Rosetta 的版本。
- ⛔ watchOS 必须 arm64，二进制体积 ≤ 75 MB。
- ⛔ 指纹识别零容忍（Guideline 3.3.9 / 5.1.2(iii)）：即使披露、即使用户授权也不允许；第三方归因 SDK 带 fingerprinting 会连带整包被拒。

**适配主线**：`NavigationSplitView` + Size Class 连续适配，不写 `if device == iPad`；iPad 必须回归 Split View / Slide Over / Stage Manager 全部比例；每个窗口用 `@SceneStorage` 独立保留导航状态；iPhone Duo 类折叠屏要求开合连续而非双套布局。

**合规**：主应用与**每个第三方 SDK** 都必须带 `PrivacyInfo.xcprivacy` 且被正确 target 引用；App Privacy 标签须与 Manifest、SDK 行为、隐私清单三方一致。

### 4.5 Windows

**交付形态**：Store 首选 MSIX（免费 Microsoft 签名 + CDN 托管 + 增量更新）；EXE/MSI 也接受但必须是**离线、自托管、提交后不变**的安装程序；Store 外用受信任 CA 证书签名的 MSIX 可直接双击安装。

**硬约束**
- ⛔ **EV 证书不再绕过 SmartScreen**。SmartScreen 是声誉驱动的：OV/EV 已签名文件在积累足够下载量前，首次下载仍显示"无法识别的应用"；唯一零警告路径是 Microsoft Store（Microsoft 证书重签）。
- ⛔ WinUI 3 跨不同 DPI 显示器拖拽**不会**自动响应 DPI 变化，必须显式声明 Per-Monitor V2 并对跨屏 DPI 变化手动重算；`AppWindow.MoveAndResize` 用物理像素，与设备无关像素混用会在 125% / 150% 缩放下产生尺寸偏差。
- ⛔ x64 + ARM64 必须同一提交捆绑（或 `.msixbundle`），仅提交 x64 会让 ARM 用户跑 Prism 模拟，续航与性能明显劣化。
- ⛔ Windows 10 已 EOL；**消费者 ESU 于 2026-10-13 结束，商业/企业 ESU 最长至 2028-01**，做企业向分发（MSIX / 内网部署）时不要把"全部已无补丁"当既成事实。新项目以 Windows 11 为设计与测试基线。

**技术栈**：原生 → WinUI 3 + Windows App SDK（**当前 Stable 为 2.6.5，2026-11-02 发布** 🔄 源文档写 2.5.1）；跨平台 → .NET MAUI 或 React Native for Windows，不要"先 WinUI 3 再回头加跨平台"。

**AI 分层**：Copilot+ PC（NPU ≥ 40 TOPS、16 GB+ RAM）用 Windows AI APIs；普通硬件用 Foundry Local（DirectX 12 GPU，含无 NPU 设备）或 Windows ML（自带 ONNX）。不要假设用户都是 Copilot+ PC。

**合规**：隐私政策 URL 必须指向政策页面本身（非主页/PDF）；同意弹窗必须在任何数据请求之前；拒绝与接受同等容易；演示账号写在提交备注首行。

### 4.6 Linux

**交付形态**：没有统一渠道，按受众矩阵分发——AppImage + deb + rpm 覆盖约 90% 桌面用户，Flatpak（Flathub）+ Snap 各再覆盖约 5%。

**硬约束**
- ⛔ glibc 基线决定一切：在 Ubuntu 24.04 上构建的包无法在 Ubuntu 22.04 / Debian 12 启动。**统一在 Ubuntu 22.04 容器构建（glibc 2.35/2.36）**，同一产物喂 AppImage / deb / rpm，不为每种格式单独编译。
- ⛔ Wayland 下 `set_outer_position()` 是协议级 no-op：托盘走 StatusNotifierItem / AppIndicator（D-Bus），弹窗菜单走 `wlr-layer-shell`，不要用 X11 绝对定位思维。
- ⛔ `XDG_SESSION_TYPE` 不可靠（Ubuntu 26.04 GDM 在 X11 会话下仍可能报 wayland，导致 Electron/Chromium 段错误）：用 `WAYLAND_DISPLAY` / `DISPLAY` 判断，并提供强制 `--ozone-platform=x11` 的可配置兜底。
- ⛔ Flatpak / Snap 沙箱是硬边界：默认无宿主文件系统、无 X11、无 system D-Bus。必须走 Portals（FileChooser / Print / Notification / Secret / DynamicLauncher / Inhibit），不要申请 `--filesystem=host` 或 `--socket=system-bus`。
- ⛔ Secure Boot 开启时未签名内核模块被拒载：DKMS 签名 + MOK 注册是必选项，`mokutil --import` 后的 MokManager 确认必须由人在物理控制台完成，不能 CI 自动化。

**身份一致性**：App ID / `.desktop` 文件名 / 窗口 `app_id` 三者必须一致，Flatpak 下还与 Flatpak ID 一致。

**服务端**：systemd unit 硬化（`User=` 非 root、`NoNewPrivileges=yes`、`ProtectSystem=strict`、`ProtectHome=yes`），日志交 journald，sudo 只给 `systemctl restart`。

## 5. 跨平台共性矩阵

真正需要"一次想清楚"的不是某个平台的细节，而是同一件事在六处的不同做法。以下四张表是抽象层的决策依据。

### 5.1 响应式布局：五种机制，一个原则

| 平台 | 官方机制 | 断点 | 绝不能做的事 |
| --- | --- | --- | --- |
| Android | `WindowSizeClass`（compact/medium/expanded） | 窗口宽度 | 用 `deviceType` 或物理设备名判断 |
| Apple | Size Class + `NavigationSplitView` | 窗口宽度，连续适应 | 写 `if device == iPad` 分支；按断点"跳变"而非连续 |
| HarmonyOS | 媒体查询 + GridRow/GridCol | 600vp | 按 deviceType 写死；忽略折痕区 |
| Web | 容器查询 `@container`（组件级）+ 少量视口断点（页面级） | 父容器宽度 | 组件内部写视口媒体查询 |
| Windows | 自适应触发器 + 窗口尺寸 API | 有效像素 | 物理像素与设备无关像素混用 |
| Linux | GTK/Qt 自适应容器 | 窗口尺寸 | 依赖绝对定位（Wayland 下无效） |

**统一原则**：布局依据是"运行时可用窗口"，不是设备型号。这条原则在六个平台完全一致，因此可以抽成一条设计铁律写进设计规范，而不是六条平台规则。

### 5.2 体积与性能预算

| 平台 | 硬上限 | 质量线 |
| --- | --- | --- |
| Android（Wear OS） | 表盘环境模式 ≤10 MB、交互 ≤100 MB | 应用 >5 MB 显著降低下载意愿 |
| HarmonyOS 元服务 | 单包 ≤2 MB、同设备类型总和 ≤10 MB；**不支持 .so**（本项目原生库无法进入元服务形态） | — |
| HarmonyOS 轻量手表 | HAP ≤20 MB，建议运行内存 <50 MB | 无后台常驻 |
| HarmonyOS 智能手表 | HAP ≤2 GB | — |
| Apple watchOS | 二进制 ≤75 MB | — |
| Web | 无硬上限 | LCP ≤2.5 s / INP ≤200 ms / CLS ≤0.1 |

**结论**：六个平台里四个有硬体积上限，且都指向同一件事——**手表与轻量形态必须独立建 module，不做手机包的裁剪版**。这条应在工程结构阶段就落实，而不是发版前救火。

### 5.3 隐私合规：一条链条，五种表述

| 平台 | 声明载体 | 官方核查方式 | 最高频拒审 |
| --- | --- | --- | --- |
| Android | Data Safety 表单 + 隐私政策 | 与 Manifest、SDK 行为交叉核对 | 表单与实际数据流不符 |
| Apple | `PrivacyInfo.xcprivacy` + App Privacy 标签 | 上传时解析 manifest，人工比对标签 | 缺隐私清单 / 第三方 SDK 未带 / 指纹识别 |
| Windows | Partner Center 数据申报 | 申报与数据流图比对、同意顺序审计 | 隐私政策 URL 指向主页、同意晚于请求 |
| HarmonyOS | AGC 隐私标签 + 隐私政策 | 同意时序 + 权限 reason 审查 | 同意前收集信息、reason 空泛 |
| Web / Linux | 隐私政策 + 真实行为 | 无审核，只有法律与用户信任 | Cookie 未设 SameSite/Secure、过度权限 |

**统一做法**：维护一份"数据流图"作为唯一事实源，五个平台的表单/清单都从这份图派生。任何新增 SDK 先更新数据流图，再更新各平台声明——顺序反过来必然出现不一致。

### 5.4 体积/签名/回滚三件事的共同点

- **签名**：所有平台的签名材料都在 Secrets，都遵守"临时落地、用完即删、不打印日志、生产加 gate"。
- **体积**：手表/轻量形态一律独立产物，不做裁剪版。
- **回滚**：只有 Web 有真正的回滚概念（不可变身份 + 原子回滚）；移动与桌面平台的"回滚"实质是"发一个更高版本号修复"，因此**发版前的灰度与 TestFlight/内测环节就是唯一的回滚手段**，不能省。

## 6. 统一发布闸门（跨平台 12 道）

任何平台发版，按顺序过闸，不跳项。前 8 道与平台无关，后 4 道按平台取值。

| # | 闸门 | 判定标准 | 适用平台 |
| --- | --- | --- | --- |
| 1 | 身份锚点未变 | 包名 / Bundle ID / Publisher / App ID / origin 与 §3.1 完全一致 | 全部 |
| 2 | 签名材料合规 | 使用发布证书，未混用调试证书；材料不在 Git | 全部 |
| 3 | 数据流图已更新 | 新增 SDK 已反映到数据流图，且五个平台声明同步 | 全部 |
| 4 | 隐私政策可访问 | HTTPS、公开、非 PDF、非登录墙、应用内可到达 | 全部 |
| 5 | 同意顺序正确 | 同意弹窗早于任何数据请求；拒绝与接受同等容易 | 全部 |
| 6 | 大屏/宽窗口可用 | sw > 600dp（或等效）下不锁方向、不禁止 resize、无内容截断 | Android / Apple / HarmonyOS / Web / Windows |
| 7 | 状态跨窗口保留 | 折叠、旋转、分屏、resize 后不丢导航栈与表单 | 全部 |
| 8 | 性能预算通过 | 对应平台阈值达标（Web CWV / 启动时间 / 冷启动） | 全部 |
| 9 | targetSdk / SDK 版本 | Android 36（Wear/AAOS 35、TV/XR 34）；Apple 26/27；Windows App SDK 2.6.x | 各自平台 |
| 10 | 架构与体积 | Android 16 KB + 64 位；Apple arm64 / watchOS ≤75 MB；HarmonyOS 元服务 2 MB/10 MB | 各自平台 |
| 11 | 分发形态正确 | Android AAB、HarmonyOS 已签名 HAP、Apple 已公证 dmg、Windows MSIX、Linux 三格式 + GPG | 各自平台 |
| 12 | 回滚/灰度就绪 | Web 四层回滚方案；移动端 TestFlight/内测已过；Windows 有预览环 | 全部 |

## 7. 风险矩阵

按"撞击概率 × 修复成本"排序。前三行是历史最高频的真实翻车点。

| 风险 | 平台 | 后果 | 定级 | 缓释措施 |
| --- | --- | --- | --- | --- |
| 第三方 SDK 原生库未 16 KB 对齐 | Android | 整个包被拒，且排查耗时 | 🔴 高 | 构建后扫描全部 .so 的段对齐，不只看自己的代码 |

| 在 Ubuntu 24.04 构建 Linux 包 | Linux | 旧系统用户静默失去更新能力 | 🔴 高 | 固定 ubuntu-22.04 容器构建，产物全格式复用 |
| 手表包直接裁剪手机包 | Android / HarmonyOS / Apple | 装不下 / 装不上 / 体积超限 | 🔴 高 | 手表独立 module，独立资源裁剪 |
| 隐私声明与实际数据流不一致 | 全平台 | 拒审或更新被阻 | 🔴 高 | 数据流图单一事实源（§5.3） |
| EV 证书被当作 SmartScreen 解决方案 | Windows | 采购成本浪费，首次下载仍警告 | 🟡 中 | 零警告只走 Store；非 Store 用 Artifact Signing 并接受信誉期 |
| HarmonyOS 用 `default` deviceTypes | HarmonyOS | 可编译、不可上架 | 🟡 中 | 用 `phone` 替代并覆盖全部目标设备 |
| Wayland 下自行定位弹窗 | Linux | 菜单/托盘错位且无报错 | 🟡 中 | SNI + layer-shell |
| 指纹识别类归因 SDK | Apple | 整包被拒，零容忍 | 🔴 高 | 上线前逐个 SDK 审查 fingerprinting 行为 |
| 大屏锁定方向 | Android | API 37 起失效，布局崩 | 🟡 中 | 现在移除锁定与 `resizeableActivity=false` |

## 10. 一句话执行口径

先用 §3 把身份与签名锚点定死，再用 §5 的四张矩阵统一抽象层（布局看窗口不看设备、体积上限集中处理手表形态、隐私用一张数据流图派生五套表单）；发版前按 §6 十二道闸门逐项过，不跳项；排期只认 §2 已生效清单——Android 36（Wear/AAOS 35、TV/XR 34）+ 16 KB、Apple 26 SDK + arm64、Windows App SDK 2.6.x + 放弃 Win10、鸿蒙 2 MB/10 MB + 3 年证书、Linux Ubuntu 22.04 基线 + Portals、Web strict CSP + INP 200 ms；四层回滚只有 Web 有，其余平台的内测与灰度就是唯一回滚手段。
